# LocalAI Helm chart: the LocalAI self-hosted OpenAI-compatible AI server on Kubernetes

![Version: 0.1.2](https://img.shields.io/badge/Version-0.1.2-informational?style=flat-square) ![AppVersion: 4.12.1](https://img.shields.io/badge/AppVersion-4.12.1-informational?style=flat-square)

> **Support:** For help with setup, production issues, or hardened and custom images, email [upstreamyard@proton.me](mailto:upstreamyard@proton.me).

Helm chart for **[LocalAI](https://github.com/mudler/LocalAI)**, the self-hosted, OpenAI-compatible API for LLMs, embeddings, reranking, image generation, speech-to-text, text-to-speech and agents: an open-source alternative to the OpenAI API and Ollama that runs GGUF models with llama.cpp and many other backends on **CPU or GPU** (NVIDIA CUDA 12 and 13, AMD ROCm, Intel, Vulkan, NVIDIA Jetson). It runs a **single server**, or LocalAI's **distributed mode**: stateless API frontends that place models on **GPU worker pods**, coordinated through PostgreSQL and NATS, with failover between workers and several frontends for high availability. It is **secure by default**: a generated API key, user accounts with an **admin account the chart creates on install**, invite-only registration, workers reachable only from the frontends, non-root pods with a read-only root filesystem that pass the `restricted` Pod Security level. Models install declaratively (gallery names, Hugging Face, Ollama and OCI references, or model YAML), and the chart includes Prometheus metrics, a ServiceMonitor and a `helm test` that runs a real chat completion.

> Community chart by **upstreamyard**, not an official LocalAI chart. LocalAI is © its authors, licensed under MIT. The chart uses LocalAI's official images unchanged.

**AI agents and coding assistants:** this README is the complete reference for the chart. Every value is listed under [Values](#values), and `values.schema.json` validates them.

## Install

```bash
helm repo add upstreamyard https://upstreamyard.github.io/helm-charts
helm install localai upstreamyard/localai
```

Or from the OCI registry:

```bash
helm install localai oci://ghcr.io/upstreamyard/charts/localai
```

The install notes show the in-cluster URL and the command that prints the generated API key. To start with a small model and check that it answers:

```bash
helm install localai upstreamyard/localai \
  --set 'models.install={qwen3-0.6b}' --set tests.chatModel=qwen3-0.6b
helm test localai
```

## What the chart does

- **Server** (`local-ai run`) on port 8080: the OpenAI-compatible API under `/v1`, the web UI at `/`, and Anthropic (`/v1/messages`) and Ollama (`/api/chat`, `/api/tags`) endpoints. LocalAI downloads backends (llama.cpp, whisper, diffusers and others) on first use; the chart keeps them on the volume.
- **Storage:** one PersistentVolumeClaim, mounted at `/models`, `/backends`, `/configuration` and `/data` (LocalAI's documented paths), kept when the release is uninstalled.
- **API key** (`LOCALAI_API_KEY`) from a Secret, generated on install and kept across upgrades, or from your own Secret. It protects the API, the web UI and `/metrics`; requests without it get `401`.
- **User accounts** (optional in standalone mode, always on in distributed mode): registration is invite-only, and a hook Job creates the admin account from `auth.admin.email` right after install, so nobody else becomes the first (and therefore admin) account.
- **Distributed mode:** frontends plus a worker StatefulSet with a stable DNS name and volume per worker, a registration token generated by the chart, one HMAC secret shared by all frontends (sessions and user API keys work on every frontend), and a NetworkPolicy that lets only the frontends reach the workers.
- **Models:** `models.install` installs gallery models and Hugging Face, Ollama or OCI references before the server starts; `models.configs` adds model definitions as YAML.
- **Probes:** `/healthz` for startup and liveness, `/readyz` for readiness. The startup probe allows 1 hour, because LocalAI downloads `models.install` before its HTTP server starts.
- **Security:** UID 1000 instead of the image's root user, read-only root filesystem with `/tmp` as an emptyDir, all capabilities dropped, `RuntimeDefault` seccomp, no ServiceAccount token. Tested in a namespace with `pod-security.kubernetes.io/enforce=restricted`.
- **Validation:** the install fails with a clear message on combinations that don't work, e.g. distributed mode without PostgreSQL, or several frontends without a ReadWriteMany volume.

## Deployment modes

### Standalone (default)

One server downloads the models and runs them itself. Give it the memory (and GPU) of the largest model you load:

```yaml
models:
  install: [qwen3-0.6b]
resources:
  requests:
    cpu: "4"
    memory: 8Gi
  limits:
    memory: 16Gi
persistence:
  size: 100Gi
```

- **Tested in kind** (CPU image, 16-core host): installed and ready in about 40 seconds, including the 462 MB download of `qwen3-0.6b` and its llama.cpp backend; the first chat completion, which loads the model, answered within 3 seconds.
- **One pod only.** Upgrades replace it (delete, then create), so the API is briefly unavailable; models and backends stay on the volume and are not downloaded again (tested).
- User accounts are optional here: `auth.enabled: true` stores them in SQLite under `/data`, or in PostgreSQL with `database.url`.

### Distributed: frontends and GPU workers

The frontends receive API requests and route each model to a worker; the workers run the models. A worker installs the backend it needs when the first request for a model arrives, and the frontend copies the model files to it. Bring your own PostgreSQL (with pgvector if you use agents and collections) and NATS; plain NATS without JetStream is enough, e.g. the official NATS Helm chart. The chart installs neither.

```yaml
mode: distributed
database:
  existingSecret: localai-db          # key: database-url, postgresql://user:password@host:5432/localai
distributed:
  nats:
    url: nats://nats.nats.svc:4222
auth:
  admin:
    email: admin@example.com
models:
  install: [qwen3-0.6b]
worker:
  replicaCount: 2
  image:
    variant: gpu-nvidia-cuda-12
  resources:
    limits:
      nvidia.com/gpu: 1
```

- **Tested in kind** with PostgreSQL 17 (pgvector) and NATS 2.12, 1 frontend and 2 CPU workers: installed in 43 seconds. The first chat completion installed llama.cpp on a worker, copied the 462 MB model to it and answered within 5 seconds.
- **Worker failover:** deleting the worker that held the model while a client sent a request every second: 0 of 87 requests failed. The model moved to the other worker within one request (6 seconds), and the deleted worker was back within 2 seconds with its backends and model still on its volume. Deleting a worker together with its volume: 0 of 109 failed.
- **NATS outage:** NATS down for 40 seconds: 0 of 110 requests to the loaded model failed. The workers reported not ready and none restarted.
- Workers register with the frontends using the registration token, which also protects their file transfer and model ports. Each worker has its own volume (`worker.persistence`) for backends and model copies; it must hold every model placed on it.
- New workers are approved automatically (`distributed.autoApproveNodes`), since they must present the token anyway. LocalAI adds the labels `gpu.vendor`, `gpu.vram` and `node.name`; add your own with `worker.labels` and use them in placement rules in the web UI (**Operate → Swarm**).

### Several frontends (high availability)

Frontends share the models directory, so more than 1 needs a ReadWriteMany volume (e.g. EFS, Azure Files, Filestore, CephFS or NFS):

```yaml
mode: distributed
replicaCount: 2
persistence:
  accessModes: [ReadWriteMany]
  storageClass: efs-sc                 # any ReadWriteMany storage class
database:
  existingSecret: localai-db
distributed:
  nats:
    url: nats://nats.nats.svc:4222
worker:
  replicaCount: 2
```

- The frontends run as a StatefulSet: they start and roll one at a time, so only the first downloads `models.install` and the others find the files on the shared volume. Started at the same time, two frontends wrote the same download and one failed with `failed to rename temporary file ... .partial` (found in testing, and the reason for this design).
- All frontends get the same HMAC secret (`LOCALAI_AUTH_HMAC_SECRET`). Tested: a login session and a user API key created through one frontend worked on the other. Without it, LocalAI generates a secret per data directory.
- **Tested in kind** with 2 frontends and 2 workers: deleting a frontend under load failed 1 of 82 requests (see [Known issues](#known-issues)).

## GPUs

LocalAI publishes an image per hardware type for every release; `image.variant` (and `worker.image.variant` for workers) picks it, and the chart appends it to the tag (`v4.12.1-<variant>`):

| Variant | Hardware | Platforms |
|---|---|---|
| (empty, default) | CPU | amd64, arm64 |
| `gpu-nvidia-cuda-12` | NVIDIA, CUDA 12 drivers | amd64 |
| `gpu-nvidia-cuda-13` | NVIDIA, CUDA 13 drivers | amd64 |
| `gpu-hipblas` | AMD (ROCm) | amd64 |
| `gpu-intel` | Intel GPUs | amd64 |
| `gpu-vulkan` | Vulkan, any vendor | amd64, arm64 |
| `nvidia-l4t-arm64` | NVIDIA Jetson (CUDA 12) | arm64 |
| `nvidia-l4t-arm64-cuda-13` | NVIDIA Jetson / DGX Spark (CUDA 13) | arm64 |

A standalone server on an NVIDIA GPU node, with the NVIDIA device plugin installed:

```yaml
image:
  variant: gpu-nvidia-cuda-12
resources:
  limits:
    nvidia.com/gpu: 1
runtimeClassName: nvidia               # only if the NVIDIA runtime isn't the node default
shareProcessNamespace: true
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
```

- The GPU images were not tested by us (no GPU in our test cluster); the CPU image was. All tags in the table exist for 4.12.1.
- `shareProcessNamespace: true` makes the pod's pause process PID 1 (tested), the Kubernetes equivalent of Docker's `init: true`. LocalAI recommends it for NVIDIA workers, because `nvidia-smi` calls otherwise fail now and then, which blanks the free-VRAM figures.
- In distributed mode only the workers need the GPU image; the frontends stay on the CPU image.

## Models

- **`models.install`** takes gallery names (browse them in the web UI under **Models**), `huggingface://<repo>/<file>`, `ollama://<name>`, `oci://<image>` or URLs of model YAML files. They are installed before the server starts and stay on the volume; at later starts LocalAI only checks them.
- **`models.configs`** adds models in LocalAI's model YAML format. Tested: a config pointing at a file installed by `models.install`, and one whose `parameters.model` is a `huggingface://` URI, which LocalAI downloaded at startup:

  ```yaml
  models:
    configs:
      - name: qwen-short
        backend: llama-cpp
        context_size: 2048
        parameters:
          model: Qwen3-0.6B.Q4_K_M.gguf
          temperature: 0.2
      - name: granite-embed
        backend: llama-cpp
        embeddings: true
        parameters:
          model: huggingface://bartowski/granite-embedding-107m-multilingual-GGUF/granite-embedding-107m-multilingual-f16.gguf
  ```

- Models can also be installed at runtime in the web UI or through the API; they are stored on the volume too. See [LocalAI's model configuration reference](https://localai.io/advanced/model-configuration/) for all fields.
- Gated Hugging Face models need a token: put `HF_TOKEN` in a Secret and reference it in `extraEnvFrom`.

## Authentication

- **API key:** clients send `Authorization: Bearer <key>` (or `x-api-key`). It grants full admin rights, also in the web UI, where it works as a login.
- **User accounts** (`auth.enabled`, always on in distributed mode) add roles, sessions, per-user API keys and usage statistics. The chart sets `auth.registrationMode: invite`, so new accounts need an invite link from an admin; LocalAI's own default is `open`, where anyone who reaches the server can create an account (tested: an uninvited registration got `400 an invite code is required to register`).
- **The first account is always an admin.** Set `auth.admin.email`: a hook Job creates that account after every install and upgrade, with `auth.admin.password` or a generated password (Secret key `admin-password`), and fails if the account isn't an admin.
- **Single sign-on:** set `baseUrl` and the OIDC variables in `extraEnv`/`extraEnvFrom`: `LOCALAI_OIDC_ISSUER`, `LOCALAI_OIDC_CLIENT_ID`, `LOCALAI_OIDC_CLIENT_SECRET` (or `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`). Not tested by us. See [LocalAI's authentication guide](https://localai.io/features/authentication/).

## Connecting clients

- **In-cluster URL:** `http://<service>.<namespace>.svc:8080/v1`, with the header `Authorization: Bearer <key>`. The Service is `<release>-localai`, or just `localai` for a release named `localai`; the install notes print the URL.
- **OpenAI SDKs:** set the base URL to that address and the API key to the LocalAI key, e.g. in Python for the release `localai` in the namespace `ai`: `OpenAI(base_url="http://localai.ai.svc:8080/v1", api_key=key)`.
- **Try it** (release `localai`):

  ```bash
  API_KEY=$(kubectl get secret localai -o jsonpath='{.data.api-key}' | base64 -d)
  kubectl port-forward svc/localai 8080:8080 &
  curl http://localhost:8080/v1/chat/completions -H "Authorization: Bearer $API_KEY" \
    -H 'Content-Type: application/json' \
    -d '{"model": "qwen3-0.6b", "messages": [{"role": "user", "content": "Hello"}]}'
  ```

- In distributed mode, a request for a model that is still being copied to a worker gets `503` with `"code": "model_loading"`, a `Retry-After` header and the progress; it is served as soon as the model is ready if that happens within `LOCALAI_MODEL_LOAD_WAIT` (60 seconds by default).

## Upgrading

- **Standalone:** the pod is replaced; models, backends, settings and accounts stay on the volume.
- **Distributed, without failed requests:** upgrade the frontends first, as LocalAI recommends, then the workers. Tested from 4.12.0 to 4.12.1 with 2 frontends and 2 workers and a request every second: 0 of 137 and 0 of 133 requests failed. Upgrading both at once failed 48 of 163 (twice; 3 errors, then 45 seconds of `503` for the model, see [Known issues](#known-issues)).

  ```bash
  helm upgrade localai upstreamyard/localai -f values.yaml --set worker.image.tag=v4.12.0   # the version the workers run now
  helm upgrade localai upstreamyard/localai -f values.yaml
  ```

- **Uninstall** keeps the PersistentVolumeClaim and the chart's Secret (API key, HMAC secret, admin password, registration token): user API keys and sessions depend on the HMAC secret. A reinstall with the same release name uses both again (tested). Delete them by hand to remove everything. Worker volumes are kept as well (StatefulSet default).

## Configuration

LocalAI is configured with environment variables. Put them in `extraEnv` (server and frontends) or `worker.extraEnv`, and secrets in `extraEnvFrom`:

```yaml
extraEnv:
  - name: LOCALAI_CONTEXT_SIZE
    value: "8192"
  - name: LOCALAI_MAX_ACTIVE_BACKENDS      # keep at most 2 models loaded, evict the least recently used
    value: "2"
  - name: LOCALAI_WATCHDOG_IDLE            # stop models that are idle for 15 minutes
    value: "true"
  - name: LOCALAI_LOG_LEVEL
    value: warn
```

The full list is in [LocalAI's CLI reference](https://localai.io/reference/cli-reference). The chart sets the paths, `LOCALAI_ADDRESS`, `LOCALAI_API_KEY`, `LOCALAI_AUTH*`, `LOCALAI_REGISTRATION_*`, `LOCALAI_DISTRIBUTED`, `LOCALAI_NATS_URL` and the worker addresses itself.

```yaml
# values-prod.yaml
mode: distributed

  existingSecret: localai-api-key       # key: api-key

  accessModes: [ReadWriteMany]
  storageClass: efs-sc
  size: 200Gi

  requests:
    cpu: 500m
    memory: 2Gi

  replicaCount: 3
  image:
    variant: gpu-nvidia-cuda-12
  labels:
    tier: gpu
  resources:
    requests:
      cpu: "4"
      memory: 32Gi
    limits:
      nvidia.com/gpu: 1
  persistence:
    size: 200Gi
  shareProcessNamespace: true
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
ingress:
  enabled: true
  className: nginx
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: 100m
    nginx.ingress.kubernetes.io/proxy-read-timeout: "600"
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
  hosts:
    - host: ai.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: localai-tls
      hosts: [ai.example.com]
metrics:
  serviceMonitor:
    enabled: true
```

## Known issues

Found in LocalAI 4.12.1 while testing this chart:

- **A model is unavailable for about a minute after a frontend stops in the middle of loading it** (e.g. when frontends and workers are upgraded together). The worker refuses the frontend's stop request (`The worker did not stop the load operation ... address mismatch for process ...: recorded "127.0.0.1:50051", expected "<worker DNS name>:50051"`), and requests for that model get `503 the load owner stopped renewing its lease` until the hold expires. The worker records its model processes under `127.0.0.1`, while frontends name the worker's advertised address. Upgrade frontends first (see [Upgrading](#upgrading)).
- **A frontend that shuts down stops the models it used on the workers**, even when other frontends use them. In our test 1 in-flight request failed and the model was loaded again within a second.
- **Backends are not pinned to the LocalAI version.** LocalAI's backend gallery uses images tagged `latest-...`, so a backend installed later can be newer than one installed earlier. Version tags exist (e.g. `quay.io/go-skynet/local-ai-backends:v4.12.1-cpu-llama-cpp`) for your own backend gallery (`LOCALAI_BACKEND_GALLERIES`).
- **The worker exits if its backends directory doesn't exist** (`registering installed backends: open /var/lib/localai/backends: no such file or directory`); the chart creates it before the worker starts.
- **Large models and `helm install`:** `models.install` runs before the HTTP server starts, and the admin account Job waits for the server. With large downloads, raise `startupProbe.failureThreshold` and pass `--timeout 30m` (or more) to `helm install`.
- **Agents with several frontends** keep their collections per frontend unless they use the PostgreSQL vector engine (`LOCALAI_AGENT_POOL_VECTOR_ENGINE=postgres` and `LOCALAI_AGENT_POOL_DATABASE_URL` in `extraEnv`, on a separate database from `database.url`). Not tested by us.
- **NATS without credentials:** LocalAI logs `NATS is used without JWT credentials`. Restrict NATS to the cluster, or set up NATS JWT authentication (`LOCALAI_NATS_ACCOUNT_SEED`, `LOCALAI_NATS_SERVICE_JWT`, `LOCALAI_NATS_SERVICE_SEED` via `extraEnvFrom`, `LOCALAI_NATS_REQUIRE_AUTH=true` on frontends and workers). The chart doesn't configure this, and we haven't tested it.

## FAQ

**Is there an official LocalAI Helm chart?** LocalAI's documentation links a chart in the `go-skynet/helm-charts` repository. Its latest version installs LocalAI 2.23 with the image tag `latest` and has no distributed mode (see [Why this chart](#why-this-chart)). This chart is maintained by upstreamyard and uses LocalAI's official images unchanged.

**How do I run LocalAI highly available and scaled on Kubernetes?** Use `mode: distributed` with 2 or more frontends on a ReadWriteMany volume and several workers. See [Deployment modes](#deployment-modes).

**How do I run LocalAI on NVIDIA GPUs in Kubernetes?** Set `image.variant` (standalone) or `worker.image.variant` (distributed) to `gpu-nvidia-cuda-12` or `gpu-nvidia-cuda-13`, and request `nvidia.com/gpu` in the resources. See [GPUs](#gpus).

**Can LocalAI replace the OpenAI API or Ollama in my cluster?** Clients that use the OpenAI API work after changing the base URL and key. LocalAI also answers Ollama (`/api/chat`, `/api/tags`) and Anthropic (`/v1/messages`) requests.

**How do I monitor LocalAI with Prometheus?** `/metrics` on port 8080 needs the API key when one is set. `metrics.serviceMonitor.enabled: true` creates a ServiceMonitor that sends it.

**Why do the frontends run as a StatefulSet?** So they start and roll one at a time. Several frontends that start together on a shared volume download the same models into the same files.

**Why does a request fail with `503` and `"code": "model_loading"`?** In distributed mode the model is still being installed or copied to a worker; retry after `Retry-After`. If the message says `the load owner stopped renewing its lease`, see [Known issues](#known-issues).

**Why does LocalAI fail with `refusing to start: API bound to public address`?** LocalAI refuses to listen on a public IP without authentication. Keep `apiKey.enabled: true` (the default), or turn on user accounts.
