# Dolt Helm chart: Dolt SQL server on Kubernetes

![Version: 0.1.2](https://img.shields.io/badge/Version-0.1.2-informational?style=flat-square) ![AppVersion: 2.6.0](https://img.shields.io/badge/AppVersion-2.6.0-informational?style=flat-square)

Helm chart for **[Dolt](https://github.com/dolthub/dolt)**, the version-controlled SQL database: a MySQL-compatible server where you branch, merge, diff and clone your data like a Git repository. It runs a single server or a **highly available primary/standby cluster** with Dolt's built-in replication. A standby takes over in about a second with one command, and rolling updates hand the primary role over first, so writes pause for under a second. Passwords are generated by default. Prometheus metrics, a ServiceMonitor, a NetworkPolicy and `helm test` are included. The chart uses DoltHub's official [`dolthub/dolt-sql-server`](https://hub.docker.com/r/dolthub/dolt-sql-server) image and was tested with Dolt 2.4.

## What the chart does

- **StatefulSet** with stable pod names (`<release>-dolt-0`, `-1`, ...) and a PersistentVolumeClaim per server for the databases, users and grants.
- **Logins:**
  - `root` with a generated password in a Secret, kept across upgrades;
  - optional database and application user (`auth.database`, `auth.username`), created by a Job after every install and upgrade.
- **Security:** non-root (UID 10001), read-only root filesystem, all capabilities dropped. Only the role labeler sidecar gets a ServiceAccount token, allowed to read and label the release's server pods. The NetworkPolicy (`networkPolicy.enabled`) limits the replication port to the release's servers.
- **Replication** (`replicaCount` 2 or more): server 0 starts as the primary and the others are read-only standbys. The primary pushes every commit, branch change, new database, user and grant to them.
- **Routing:** a sidecar labels each pod with its current role (`dolthub.com/cluster_role`), and the read-write Service selects the primary, so it follows every failover within 2 seconds.
- **Failover:** `promote.sh` in every pod switches the primary, either planned without data loss or forced when the primary is down. Before a primary's pod stops (rolling update, node drain, `kubectl delete pod`), it hands the role to a caught-up standby.
- **Metrics:** `metrics.enabled` serves Prometheus metrics on port 11228; `metrics.serviceMonitor.enabled` adds a ServiceMonitor.
- **No usage events:** Dolt sends anonymous usage events to DoltHub by default. The chart turns this off; `usageMetrics: true` turns it back on.
- **Your own settings:** `config` is merged into each server's `config.yaml`.

## Deployment modes

### Single server (default)

One server on a PersistentVolumeClaim. If the pod or its node fails, Kubernetes restarts it on the same volume.

```yaml
auth:
  database: app
  username: app        # password generated, see the install notes
persistence:
  size: 20Gi
```

### High availability: primary and standbys

```yaml
replicaCount: 3
auth:
  database: app
  username: app
networkPolicy:
  enabled: true
podAntiAffinityPreset: hard   # one server per node
```

Tested in kind with 3 servers and a client writing 3 to 4 rows per second:

| Event | Writes paused | Data |
|---|---|---|
| Planned failover with `promote.sh` | about 1 s | nothing lost |
| Rolling `helm upgrade` (also Dolt 2.4.1 → 2.4.2), 33 s for 3 servers | under 1 s (1 to 3 failed writes) | nothing lost |
| Primary hangs, then `promote.sh --force` | until you run it | the old primary rejoins as a standby and catches up by itself |
| Scaling from 1 to 3 servers and back | while the pods restart | existing databases, branches and users reach the new standbys |

**Failover is manual.** Dolt never promotes a standby by itself, and neither does the chart. A crashed server restarts in its pod and keeps its role, but if the primary hangs or its node is lost, promote a standby:

```bash
# Planned: the primary hands over its last writes first. Refuses if a server is unreachable.
kubectl exec dolt-1 -c dolt -- /etc/dolt/promote.sh
# The primary is down: promote anyway. Writes it hadn't replicated yet are lost.
kubectl exec dolt-1 -c dolt -- /etc/dolt/promote.sh --force
```

Each switch raises the cluster's epoch. A former primary that comes back sees the higher epoch, becomes a standby and takes the new primary's data. In our test a frozen primary resumed after a forced failover and ended with the same rows as the others, without a split brain.

Things to know:

- **Every write goes to every standby**, so more standbys add network and disk traffic on the primary. Two or three servers suit most setups.
- **Changing `replicaCount` restarts all servers**, because each one's peer list changes. Volumes of servers removed by scaling down are deleted: they are replicas, and kept they would come back later with an old role.
- **Replication is plain HTTP** inside the cluster, authenticated with keys each server generates. Turn on `networkPolicy.enabled` so only the release's servers reach port 50051.

## Connecting clients

Dolt speaks the MySQL protocol, so any MySQL client, driver or ORM works:

- **Read-write:** `<release>-dolt.<namespace>.svc:3306`, the primary.
- **Read-only** (replication only): `<release>-dolt-read.<namespace>.svc:3306`, all servers. Standbys reject writes with `Database ... is read-only`.

```bash
mysql -h dolt.default.svc -u app -p app
```

On a planned failover or rolling update, Dolt closes the old primary's connections, so use a connection pool that reconnects, and retry failed transactions.

## Production example

```yaml
# values-prod.yaml
replicaCount: 3
auth:
  existingSecret: dolt-auth        # keys: root-password, user-password
  database: app
  username: app
config:
  listener:
    max_connections: 500
persistence:
  size: 100Gi
  storageClass: fast-ssd
metrics:
  enabled: true
  serviceMonitor:
    enabled: true
networkPolicy:
  enabled: true
  allowedClients:
    - podSelector:
        matchLabels:
          app: my-app
resources:
  requests:
    cpu: "1"
    memory: 4Gi
  limits:
    memory: 8Gi
podAntiAffinityPreset: hard
```

## Your own configuration

- **Server settings:** anything from Dolt's [`config.yaml` reference](https://www.dolthub.com/docs/sql-reference/server/configuration/) goes in `config`, e.g. `behavior.dolt_transaction_commit`, `system_variables` or `listener.max_connections`. The chart sets `data_dir`, `listener.host`/`port`, the metrics address and `cluster`.
- **TLS for clients:** mount a Secret with the certificate and key, and point `config.listener.tls_cert` and `tls_key` at them. Clients can then connect with TLS (tested with `mysql --ssl-mode=REQUIRED`). `require_secure_transport` isn't supported, because the role labeler, the init Job and `helm test` connect without TLS.

  ```yaml
  extraVolumes:
    - name: tls
      secret:
        secretName: dolt-tls      # keys: cert.pem, key.pem
  extraVolumeMounts:
    - name: tls
      mountPath: /tls
      readOnly: true
  config:
    listener:
      tls_cert: /tls/cert.pem
      tls_key: /tls/key.pem
  ```
- **Passwords:** `root` gets its password only on the first start of each server. To change it later, run `ALTER USER 'root'@'%' IDENTIFIED BY '...'` on the primary and update the Secret, which the role labeler and `helm test` use. The application user's password is set from the Secret on every upgrade.
- **SQL shell:** `kubectl exec -it dolt-0 -c dolt -- bash -c 'DOLT_CLI_PASSWORD=$DOLT_ROOT_PASSWORD dolt --host 127.0.0.1 --user root --no-tls sql'`.

## FAQ

**Is there an official Dolt Helm chart?** No. DoltHub doesn't publish one, and Artifact Hub listed no other Dolt chart when we built this one. This chart is maintained by upstreamyard.

**How do I run Dolt highly available on Kubernetes?** `replicaCount: 3` with this chart. See [High availability](#high-availability-primary-and-standbys).

**Does Dolt fail over automatically?** No. Dolt doesn't elect a new primary by itself, so the chart doesn't either: an automatic promotion during a network split could create two primaries. Run `promote.sh` (above), from your runbook or your alerting.

**How do I monitor Dolt with Prometheus?** `metrics.enabled=true` and `metrics.serviceMonitor.enabled=true`. Besides connections, query durations and Go runtime metrics, `dss_is_replica` shows each server's role per database, and on the primary `dss_replication_lag` the lag per standby (milliseconds; `-1` on standbys). Replication errors are in the SQL table `dolt_cluster.dolt_cluster_status` on the primary.

**Why does a write fail with "Database ... is read-only"?** The client is connected to a standby: through the `-read` Service, or through a connection opened before a failover. Send writes to the read-write Service and reconnect after errors.

**Does the chart use doltclusterctl?** No. The chart's sidecar and `promote.sh` take its place and use only the Dolt image. They set the same pod label (`dolthub.com/cluster_role`).

## Known issues

- After a server restarts, Dolt keeps connecting to the replication address it had resolved before, so pointing peers at the headless Service's pod names breaks replication to that server for about 30 seconds. The chart gives each server its own ClusterIP Service for replication (`<release>-dolt-<n>-replication`), whose address stays the same.
- During a primary's handover, Dolt blocks writes for up to 10 seconds while it waits for every standby, including users and grants. A standby that restarted moments earlier can need that long. The chart waits 10 seconds (`cluster.minReadySeconds`) after each restarted server before stopping the next one, which kept the pause under a second in our tests.
